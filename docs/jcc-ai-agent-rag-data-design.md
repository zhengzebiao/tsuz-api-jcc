# 金铲铲资料 AI Agent / RAG 数据设计建议

## 结论

要基于金铲铲官方资料构建稳定的 AI Agent / RAG 咨询工具，建议将业务所需的官方 JSON 定时同步到自己的存储中，并区分以下三个环节：

1. 下载并留存原始 JSON；
2. 解析、关联并写入结构化数据库或文档库；
3. 将适合语义检索的字段整理成文本，再生成向量。

JSON 可以作为向量化的数据来源，但不建议将整个 JSON 文件原样序列化后只生成一个向量。向量化的主要对象应是名称、描述、技能、效果和攻略等文本；ID、数值、版本以及实体关系应保存在结构化数据库和向量元数据中。

推荐采用：

> 原始 JSON 快照 + 结构化数据库 + 全文检索 + 向量检索

而不是只依赖向量数据库。

## 推荐架构

```text
腾讯官方 JSON/CDN
        ↓ 定时同步
原始 JSON 快照
        ↓ 解析、关联、清洗
结构化数据库/文档库
        ↓ 生成语义文档
Embedding 向量化
        ↓
向量数据库
        ↓
AI Agent：结构化查询 + 全文检索 + 向量检索
```

建议保存三种形态的数据：

- 原始官方 JSON：用于追溯、重新处理及保存历史版本；
- 结构化实体与关系：用于准确查询属性、数值和关联关系；
- 文本及其向量：用于自然语言、模糊意图和攻略类语义检索。

## 原始数据层

建议按版本保存完整的官方数据文件，例如：

```text
raw/
  18.18.1c-S19/
    versiondataconfig.json
    chess.json
    race.json
    job.json
    trait.json
    equip.json
    hex.json
    adventure.json
    galaxy.json
    lineup_detail_total.json
```

保存原始数据有以下作用：

- 官方字段变化后可以重新处理；
- 保留历史赛季和历史版本；
- 调整分块或向量化规则后可以重新生成文档；
- 避免旧版本官方 URL 将来失效导致数据丢失；
- 出现解析或内容错误时可以追溯原始数据。

图片通常不需要向量化。文本咨询工具可以先保存图片 URL；是否下载图片到本地，应根据历史留存、高可用及素材授权要求单独决定。

## JSON 如何用于向量化

准确地说，不是直接“向量化 JSON”，而是：

1. 解析 JSON；
2. 关联 ID 对应的实体；
3. 将数据转换成语义完整、可独立理解的文本；
4. 对文本调用 Embedding 模型；
5. 将向量与结构化元数据一起保存。

例如，英雄原始数据可能为：

```json
{
  "id": "11500",
  "name": "奥恩",
  "class": "341",
  "species": "450",
  "initHP": "700",
  "skillName": "风箱炎息",
  "skillDesc": "主动：获得持续4秒的护盾……"
}
```

不应只把 ID 和所有字段无差别拼接。应先将 `species`、`class` 等字段关联为可读名称，再生成文档：

```text
数据类型：英雄
赛季：自然之力
版本：18.18.1c-S19
英雄名称：奥恩
费用：1费
特质：永恒之森
职业：护卫

基础属性：
生命值700，攻击力40，护甲40，魔抗40，攻击速度0.60，
攻击距离1，初始法力值40，最大法力值100。

技能名称：风箱炎息
技能效果：
主动获得持续4秒的护盾，并对锥形范围内的敌人造成魔法伤害。
奥恩还可以通过格挡伤害积累锻炉能量并获得神器锻造器。

技能星级数值：
护盾为400/460/550，伤害为200/300/450。
```

对这类文本生成向量，语义检索效果通常比直接嵌入原始 JSON 更好。

## 哪些字段适合向量化

适合向量化的内容包括：

- 英雄名称、技能名称和技能描述；
- 羁绊名称、规则说明及各档位效果；
- 强化符文名称及效果；
- 装备名称、基础属性及被动效果；
- 特殊机制名称和说明；
- 开局奇遇名称和说明；
- 阵容运营说明；
- 前中后期过渡策略；
- 装备思路；
- 站位说明；
- 克制关系；
- 将英雄协同关系整理成的自然语言描述。

这些文本适合回答：

- 有哪些适合连败经济的强化符文？
- 哪些装备能提高前排生存能力？
- 奥恩和哪些英雄有羁绊协同？
- 自然之力有哪些开局增加装备的奇遇？
- 找一套以厄斐琉斯为主 C 的阵容。
- 什么阵容比较克制阿狸？

## 哪些字段不应只依靠向量检索

以下内容更适合结构化数据库或关系查询：

- 英雄 ID、装备 ID；
- 费用、生命值、护甲等精确数值；
- 版本号和赛季；
- 羁绊档位及人数；
- 装备合成材料 ID；
- 图片 URL；
- 精确的英雄—羁绊关系；
- 精确的阵容—英雄—装备关系；
- 棋盘站位坐标。

例如用户询问“奥恩有多少护甲”，应直接查询英雄的结构化字段，而不是依赖语义相似度。

用户询问“无尽之刃怎么合成”，应查询 `synthesis1` 和 `synthesis2`，再关联装备表得到：

```text
暴风之剑 + 拳套 = 无尽之刃
```

这类问题使用数据库查询更准确、更可验证。

## 混合检索设计

建议让 Agent 根据问题选择不同的检索方式：

```text
用户问题
  ├─ 实体识别：英雄、装备、羁绊、阵容、赛季
  ├─ 结构化查询：精确属性、数值和关系
  ├─ 全文检索：名称、别名和准确术语
  └─ 向量检索：相关效果、玩法意图和攻略
              ↓
         合并、去重、重排
              ↓
       基于检索证据生成回答
```

### 结构化查询适合处理

- 精确查找英雄和装备；
- 查询英雄属性；
- 查询装备合成；
- 查询英雄所属羁绊；
- 查询共享羁绊的英雄；
- 查询阵容包含的英雄；
- 查询英雄在特定阵容中的装备；
- 按费用、职业、特质和版本筛选。

### 全文检索适合处理

- 英雄、装备和羁绊的准确中文名称；
- 常见简称和别名，例如“羊刀”“青龙刀”“法爆”；
- “重伤”“灼烧”“破甲”“回蓝”等准确游戏术语。

### 向量检索适合处理

- 模糊描述；
- 用户意图；
- 效果相似性；
- 战术建议；
- 用户不知道准确名称时的搜索；
- 攻略、运营、站位和克制关系。

## 向量文档的推荐粒度

不要把整个 `chess.js`、`equip.js` 或全部攻略作为一个文档生成一个向量。一个超大文档无法准确表达其中所有实体，也不利于定位来源。

### 英雄

数据较短时，每个英雄生成一条文档：

```text
hero:18:S19:18.18.1c:11500
```

数据较长时，可以按主题拆分：

```text
hero:18:S19:18.18.1c:11500:overview
hero:18:S19:18.18.1c:11500:skill
hero:18:S19:18.18.1c:11500:synergy
hero:18:S19:18.18.1c:11500:lineup-equipment
```

### 装备

每件装备生成一条文档：

```text
equipment:18:S19:18.18.1c:2001
```

内容可包含：

- 装备名称；
- 装备类型；
- 基础属性；
- 装备效果；
- 合成方式；
- 常见别名。

### 羁绊

每个特质或职业生成一条文档。建议将同一羁绊的全部档位放在一起，因为各档位存在连续语义：

```text
trait:18:S19:18.18.1c:450
```

例如：

```text
永恒之森：
激活人数为3、5、7、9、11。
3永恒之森：……
5永恒之森：……
7永恒之森：……
```

### 强化符文

每个强化符文生成一条文档，并在元数据中保留强化等级：

```text
augment:18:S19:18.18.1c:1006
```

### 特殊机制

`adventure.js` 中同名机制可能存在不同价格或不同效果版本，因此建议：

- 每条原始记录单独保存；
- 元数据保留 `adventureId` 和 `price`；
- 文本中明确写出消耗和效果。

### 开局奇遇

每条 `galaxy.js` 记录生成一条文档，保留名称、效果、图标、版本和来源信息。

### 阵容攻略

每套阵容至少生成一条综合文档。攻略较长时，应按主题拆分：

```text
lineup:4838:overview
lineup:4838:early-game
lineup:4838:operation
lineup:4838:positioning
lineup:4838:equipment
lineup:4838:counters
```

同一阵容的分块通过 `parent_id: 4838` 关联。

分块时优先遵循实体和主题边界，不要只按固定字符数机械切割。只有单个主题仍然过长时，再使用带少量重叠的长度分块。

## 向量元数据设计

向量记录不应只有 `text` 和 `vector`，还应保存支持过滤、关联和追溯的元数据：

```json
{
  "document_id": "hero:18:S19:18.18.1c:11500:skill",
  "parent_id": "hero:18:S19:18.18.1c:11500",
  "entity_type": "hero",
  "entity_id": "11500",
  "entity_name": "奥恩",
  "mode": "18",
  "mode_name": "自然之力",
  "season": "S19",
  "version": "18.18.1c",
  "set_id": "18",
  "map_id": "1",
  "price": 1,
  "trait_ids": ["450"],
  "trait_names": ["永恒之森"],
  "class_ids": ["341"],
  "class_names": ["护卫"],
  "section": "skill",
  "source_file": "chess.js",
  "source_url": "https://game.gtimg.cn/.../chess.js",
  "source_updated_at": "2026-09-02 19:19:44",
  "content_hash": "..."
}
```

这样用户指定“自然之力”时，可以先过滤：

```text
mode = 18
season = S19
version = 当前版本
```

再执行全文或向量检索，避免召回其他赛季的同名英雄、旧技能或旧装备效果。

## 协同英雄的建模

官网英雄数据没有单独保存固定的“协同英雄”列表。官网前端的逻辑是：

1. 读取当前英雄的特质和职业；
2. 查询拥有相同特质或职业的其他英雄；
3. 排除当前英雄；
4. 按共享羁绊分组展示。

因此，协同英雄应作为结构化关系计算，而不是主要依赖向量检索。可以维护：

```text
hero
trait
hero_trait
```

或者等价的英雄—特质、英雄—职业关联表。

向量文档中可以额外写入协同关系，以支持“哪些英雄适合搭配奥恩”之类的自然语言搜索；但最终回答精确列表时，建议使用关系查询。

## 推荐装备的建模

英雄静态数据中没有唯一的通用推荐装备。推荐装备来自官方阵容攻略，因此不能把某套阵容的出装直接视为英雄的永久属性。

建议保存阵容场景关系：

```json
{
  "lineup_id": "4838",
  "hero_id": "14509",
  "hero_name": "厄斐琉斯",
  "is_carry": true,
  "equipment_ids": ["2010", "2013", "2001"],
  "equipment_names": [
    "鬼索的狂暴之刃",
    "海妖之怒",
    "无尽之刃"
  ]
}
```

对应的向量文本可以为：

```text
在“永森月男”阵容中，厄斐琉斯是核心英雄。
推荐装备为鬼索的狂暴之刃、海妖之怒和无尽之刃。
该推荐属于特定阵容，不代表厄斐琉斯在所有阵容中的唯一推荐。
```

当用户询问“厄斐琉斯出什么装备”时，建议：

1. 查询所有包含厄斐琉斯的官方阵容；
2. 优先统计 `is_carry_hero = true` 的记录；
3. 按阵容评级、发布时间及装备出现频率排序；
4. 区分主流出装、备选装备及不同阵容场景；
5. 返回推荐来源和所属阵容，不输出没有依据的唯一答案。

## 同步与增量向量化

推荐根据版本配置执行增量同步：

```text
每隔30～60分钟读取 versiondataconfig.js
                ↓
当前 version 是否改变？
        ├─ 否：结束
        └─ 是：下载新版全部文件
                    ↓
                校验 JSON
                    ↓
              结构化转换
                    ↓
              生成内容哈希
                    ↓
          只向量化新增或变化的文档
                    ↓
              原子切换当前版本
```

建议为规范化后的文档计算内容哈希：

```text
content_hash = SHA256(normalized_text)
```

处理规则：

- 哈希未变化：复用现有向量；
- 哈希变化：重新生成并更新向量；
- 新文档：新增向量；
- 当前版本删除的文档：标记失效，而不是立即永久删除；
- 新版本：旧版本保留为历史数据，默认检索仅过滤当前版本。

版本切换应在全部文件下载、解析、关联和校验成功后完成。同步失败时继续提供最后一个成功版本，避免局部新版数据与旧版数据混用。

| 用户问题 | 推荐检索路线 |
|---|---|
| 奥恩护甲多少？ | 英雄结构化字段查询 |
| 无尽之刃怎么合成？ | 装备及合成关系查询 |
| 有哪些能回蓝的装备？ | 属性/全文检索 + 语义检索 |
| 有哪些适合连败运营的强化符文？ | 强化符文向量检索 |
| 厄斐琉斯推荐什么装备？ | 阵容—英雄—装备关系聚合 |
| 奥恩和谁协同？ | 共享特质/职业的关系查询 |

## 回答质量建议

Agent 生成回答时，建议同时返回：

- 数据所属模式、赛季和版本；
- 使用的实体及准确数值；
- 推荐装备所属的具体阵容；
- 数据来源文件或 URL；
- 必要时标明数据更新时间；
- “官方静态资料”“官方阵容攻略”和“系统推导结果”的来源类型。

需要明确区分：

- 官方直接记录：技能、属性、装备效果、攻略出装等；
- 官网前端推导：共享羁绊形成的协同英雄；
- 系统聚合结果：跨阵容统计得到的通用装备推荐；
- 模型生成建议：基于以上证据做出的解释或战术分析。

## 最终建议

当前资料规模不算大，但数据类型复杂且包含大量精确关系，因此不应将向量数据库作为唯一知识层。

最稳妥的实现方案是：

1. 下载并保存当前业务需要的全部官方 JSON；
2. 保存每个版本的原始快照；
3. 将英雄、羁绊、装备、强化符文、特殊机制、开局奇遇和阵容攻略结构化入库；
4. 建立英雄—羁绊、装备—合成材料、阵容—英雄—装备等关系；
5. 将描述性内容按实体和主题生成中文语义文档；
6. 对这些文本生成 Embedding；
7. 查询时先识别实体和版本，再组合结构化、全文和向量检索；
8. 让 Agent 基于检索证据回答，并附上版本和来源。

简而言之：

> 资料建议下载并留存；JSON 完全可以支持向量化，但应先解析、关联并转换成语义完整的文本。文本用于 Embedding，精确数值和关系用于结构化查询，二者结合才能得到稳定、准确且可追溯的 AI 咨询工具。
